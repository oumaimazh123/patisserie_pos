# TODO — Android and Windows versions

This document is the implementation checklist for adding a Windows 10/11
version with Kotlin Multiplatform (KMP) and Compose Multiplatform while keeping
the existing Android application operational.

The target is functional parity: Android and Windows must follow the same
business rules and provide the same POS capabilities. Platform-specific code is
allowed only where the operating systems require different implementations.

## Non-negotiable requirements

- [ ] Keep the existing Android application working throughout the migration.
- [ ] Do not rewrite the application as an unrelated second product.
- [ ] Keep one repository and one shared business-logic source of truth.
- [ ] Preserve the current Android package ID: `ma.elaroui.pos`.
- [ ] Preserve existing Android Room data and all database migrations.
- [ ] Keep the application offline-first on Android and Windows.
- [ ] Preserve French, English, Arabic, and RTL behavior.
- [ ] Preserve roles, permissions, audit history, reports, and register rules.
- [ ] Support Windows 10/11 64-bit.
- [ ] Deliver a self-contained Windows installer that does not require the
      client to install Java.
- [ ] Never put a licensing private key or an application-signing key in either
      application.

## Licence policy

One purchased licence activates exactly one chosen installation:

- one Android device, or
- one Windows computer.

The licence must not work on a second installation. Android and Windows can use
the same licence-signing key pair, but every signed licence must be bound to the
platform and the installation ID contained in a request generated by the app.

- [ ] Add `platform` to licence requests and signed licence payloads.
- [ ] Use explicit platform values such as `ANDROID` and `WINDOWS`.
- [ ] Generate the installation ID inside the application; never ask a client
      to type or invent one.
- [ ] Android: preserve the existing installation ID during normal upgrades.
- [ ] Windows: generate a random installation ID on first launch and store it
      in protected, persistent per-installation storage.
- [ ] Do not base the Windows installation ID only on MAC address, disk serial,
      username, or another replaceable hardware property.
- [ ] Ensure an Android licence cannot activate Windows and a Windows licence
      cannot activate Android.
- [ ] Ensure copying a licence to another device produces a clear
      wrong-device error.
- [ ] Preserve activation during a normal application update.
- [ ] Define and document the procedure for moving a licence to a replacement
      device.
- [ ] Keep the seven-day demonstration period equivalent on both platforms.
- [ ] Detect expiry and significant clock rollback consistently.
- [ ] Add common tests for valid, expired, invalid, wrong-device,
      wrong-platform, and tampered licences.
- [ ] Update the offline licence generator to consume the complete request code
      and sign the platform field.
- [ ] Keep `D:\POS-Licensing` and all private material outside Git and outside
      client delivery packages.

## Deferred synchronization decision

Android and Windows versions having the same features does not automatically
mean they share live data.

For the first Windows release:

- [ ] Treat each licensed installation as a standalone offline POS unless a
      separate synchronization design is approved.
- [ ] Never open the same SQLite database over a Windows network share.
- [ ] Do not silently invent cloud or LAN synchronization.

If a client later needs several devices to share orders in real time, plan a
separate architecture:

- local server on the main Windows PC;
- authenticated LAN API;
- conflict and retry rules;
- device discovery;
- offline queue;
- schema/version negotiation;
- backup ownership and server recovery.

This synchronization work must be estimated, implemented, secured, and tested
as its own project phase.
